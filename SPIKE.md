# Noren feasibility spike — Arc testnet fork

**Decision: GO for the specified proving and SDK kill criteria.** The pinned
Kohaku package accepts our Entrypoint on chain 5042002. A real Groth16 proof
with `processooor = NorenCheckout` verified in the unmodified 0xbow pool.
This is a local-fork result, not a live Arc deployment.

## Reproduce

Requirements: `pnpm` 10, Node 26, Foundry (`forge`, `anvil`), and network access
for read-only Arc RPC fork state. From the repo root:

```sh
pnpm install --store-dir './.pnpm-store'
pnpm spike
```

`pnpm spike` builds the Solidity contracts, starts **one** silent Anvil process
with `--fork-url https://rpc.testnet.arc.io --chain-id 5042002 --port 8645`,
deploys the 0xbow stack and checkout, builds a Kohaku deposit, posts an ASP
root, generates two proofs serially, generates `test/fixtures/Fixture.sol`,
runs the Foundry fork tests, pays, refunds, checks the refund inbox, and kills
Anvil by its child PID on exit. It only sends transactions to `127.0.0.1:8645`.
The fork must be allowed to bind port 8645. The proof fixture is tied to that
fork's deployment and is regenerated by every run.

The requested Kabuto pnpm store was read-only to this workspace: pnpm got
`EPERM` creating its v10 directory. The repo-local `.pnpm-store` is ignored by
Git. The lockfile pins the dependencies.

## Pinned versions and local patch

`@kohaku-eth/privacy-pools@0.1.0-alpha.27` was published **2026-10-21
07:10:49 UTC** according to `npm view ... time --json`. At the start of this
run (2026-11-05 22:39 UTC), it was older than 14 days. Alpha.28 was published
2026-10-22 23:29 UTC and had not yet passed 14 days, so it was not used for
the final run. The package uses
`@fatsolutions/privacy-pools-core-circuits@1.0.5` and its published Groth16
artifacts. The Solidity core is 0xbow commit
`df4bf730214bf9d0c717a9258f7a74861758c269`, compiled with solc 0.8.28.

Kohaku accepts `{ entrypoint: { address, deploymentBlock } }` on 5042002.
Its public `prepareUnshield` assumes an Entrypoint relayer withdrawal, so
`patches/apply-kohaku.mjs` adds a direct-withdrawal branch to the bundled
`getWithdrawalPayloads`. The branch accepts a caller-supplied `Withdrawal`,
computes its context with Kohaku's `calculateContext`, and invokes the
existing `withdrawThunk` and prover. `packages/spike/src/run.ts` calls that
branch via a thin wrapper. The upstream PR should expose
`prepareUnshield({ processooor, data })` and carry that tuple through the
public API with no relayer quote. A second upstream change should add Arc's
chain config and document its RPC log window.

## Measurements

On this laptop, for the final alpha.27 run, the first proof in a fresh Node
process took **2.106 s** wall clock and the next proof took **1.892 s**.
An earlier fresh alpha.27 run measured 2.379 s and 1.894 s.
An earlier first invocation with alpha.28 (before correcting the age pin)
took 5.785 s, illustrating OS/artifact cache effects. These are laptop
measurements, not browser or phone measurements. The 30 s kill threshold was
not approached.

| Transaction | Gas used, final alpha.27 run |
| --- | ---: |
| 10 USDC deposit via Entrypoint | 352,788 |
| 4 USDC invoice withdrawal via NorenCheckout | 583,445 |
| 2 USDC shielded refund | 361,434 |

**Arc USDC fork limitation:** Arc's USDC proxy delegates transfers to the
native bridge at `0x1800…`; stock Anvil executes that address as `0x01` and
returns `StackUnderflow` on `transfer`, including a zero-value transfer.
`eth_call` on the real Arc RPC returns true for a zero-value transfer. To run
the pool and verifier on the fork without sending public transactions, the
script uses `anvil_setCode` at the real USDC address for an Anvil-only ERC20
shim (`ForkUSDC.sol`), then `anvil_setStorageAt` to fund the local deployer.
The real 0xbow Entrypoint, pool, and both Groth16 verifiers are **not**
mocked. These gas figures include the shim's ERC20 transfer cost and must be
remeasured on live Arc or an Anvil release that supports Arc's native bridge.

## Tests

`pnpm spike` reported **8 passed, 0 failed, 0 skipped** Foundry fork tests
using the real SDK-generated proof and unmodified 0xbow pool/verifier:
successful payment, replay (`AlreadyPaid`), changed registered payee
(`ContextMismatch` from the pool), expiry, refund deposit using the customer's
precommitment, oversized refund, second refund rejection, and wrong
processooor. After the Foundry
tests, the script made an actual local-fork payment and refund. A separate
Kohaku wallet at refund account index 1 discovered **2,000,000 USDC base units
(2 USDC)** as pending through `sync()` and `balance()`.

`NorenCheckout` rejects a withdrawal whose gross amount differs from the
invoice amount. Thus no surplus is left in the contract. Refunds are one
transaction per invoice, including partial refunds, and cannot exceed the
original payment.

## Open risks

- The fresh pool has an anonymity set of one in this spike. It offers no
  meaningful anonymity until many independent deposits exist.
- A newly posted ASP root invalidates an in-flight proof. Batch postman
  updates and re-prove after `IncorrectASPRoot`.
- Refunds remain pending until the ASP approves their new labels. The spike
  verifies wallet discovery, not automatic postman approval of refunds.
- Browser and phone proving time, artifact download, and memory remain
  unmeasured. The laptop result is below the kill threshold.
- Arc's native USDC bridge behavior and transaction gas cannot be fully
  checked with stock Anvil; use a compatible fork or live testnet after
  separate authorization and testnet funding.
- Merchant payouts and payment amounts are public after withdrawal. The
  proof hides which shielded depositor paid, subject to anonymity set size.

## Review fix (Claude, Nov 6)

`pay` was callable by anyone, and the invoice fields come from the customer's own withdrawal data. An attacker could therefore pay a merchant's invoice id first (any amount) and block the real customer with `AlreadyPaid`. `pay` now requires `msg.sender == merchant` (the merchant relays its own invoices, as designed), with a new test `testOnlyMerchantCanSubmitItsInvoice`; the tamper test now submits as the tampered merchant so the pool's own context check is still what rejects it. Re-run of `pnpm spike` after the fix: **GO**, 9/9 Foundry tests, cold proof 2.12 s / warm 1.89 s, withdrawal 583,473 gas, deposit 352,788 gas, refund 361,434 gas, refund discovered by the customer's Kohaku wallet as 2 USDC pending.
